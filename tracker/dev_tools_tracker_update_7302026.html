Why not CodeCommit — the short version

Kept brief here; the long-form case is in the main tracker. Three things matter.

  • CodeCommit is git hosting, not a development platform. It stores and versions code competently. The pull-request culture, code owners, repository rulesets, and merge gates — the part that makes review an enforceable control rather than a habit — is what GitHub is actually being bought for.
  • Roadmap stability has a price. AWS de-prioritized CodeCommit for sixteen months before reversing course, and moved the code-review line from CodeGuru Reviewer to Amazon Q mid-stream. A decade-long foundational choice shouldn’t rest on one vendor’s shifting internal priorities for a single line-item product.
  • Choosing CodeCommit doesn’t avoid the assembly problem, it guarantees it. Every row in the table below that GitHub covers as a platform feature becomes a separate AWS service with its own console, IAM policy set, and bill — and the secret-protection row has no managed AWS answer at any price.

Inside the two add-ons — what the $19 and the $30 actually containAli’s ask

These are sold as separate products, so they can be bought separately. Here is what is in each one, stated at the feature level rather than the marketing level.

$19 / active committer / month

Secret Protection

The one product with no equivalent anywhere else in this document. Everything here is server-side, which is the entire point.

  • Push protection — the push is rejected at GitHub’s door if it contains a recognized credential. A local hook can be skipped or never installed; this cannot be.
  • Full-history scanning across every branch and every commit ever made, against 200+ partner credential patterns — not just what’s being pushed today.
  • Validity checks — tells you whether a leaked credential is still live, which is the difference between an incident and a cleanup task.
  • Partner revocation flows — for supported providers, GitHub notifies the issuer directly so the credential can be killed without us chasing it.
  • Custom patterns and delegated bypass — our own internal credential formats, plus an approval trail whenever someone legitimately needs to override a block. The bypass itself is auditable.

$30 / active committer / month

Code Security

Application security in the pull request. The honest framing: some of what people assume is in here is already free, and the paid part is the enforcement.

  • CodeQL static analysis on every pull request — treats the codebase as a queryable database, which is why it finds data-flow bugs that pattern matchers miss.
  • Copilot Autofix — a suggested patch attached to the finding, so a developer resolves it in the review rather than opening a ticket about it.
  • Dependency review as a merge gate — blocks a PR that introduces a vulnerable or newly-flagged dependency. Note: Dependabot alerts and version bumps are free on all plans; the blocking gate is what’s paid for.
  • Org-wide security configurations — one policy applied to every repository, including ones created next year, instead of per-repo settings that drift.
  • Security overview and campaigns — the cross-repository dashboard, plus the ability to drive a class of finding to zero as a tracked effort. This is what makes remediation reportable.

If we could only buy one, buy Secret Protection. It’s the cheaper of the two, and it’s the only capability in this entire document with no alternative at any price — open source, AWS, or otherwise. Every other security function here has a credible substitute somewhere in the gap table below. A server-side push block does not.

What Claude Code covers on its ownAli’s ask

Carried forward from the earlier review, because it bears directly on the Secret Protection line: can the agent just catch this before a push?

It works, with an asterisk that matters to an auditor. Claude Code reads everything it commits, and in practice it flags an obvious API key in a diff and refuses to push. But that is the model’s judgment, not an enforced control — and “the AI usually notices” is not a control statement anyone will accept. The fix is cheap and worth doing regardless: wire a Claude Code hook (or a plain git pre-push hook) that runs gitleaks before any push completes, so it’s deterministic and applies whether a person or an agent is driving. Defence in depth, in order of strength: Secret Protection (server-side, unskippable) → the hook (local, deterministic) → Claude’s own awareness (a useful extra pair of eyes, free with the AI decision).

  • Claude Code works fine with managed environment variables — it reads the runtime environment like any other process, so the in-product secrets pattern needs no special handling. No credential is ever pasted into code or a config file for the agent’s benefit.
  • What it doesn’t replace: it is not a package registry, a CI runner, or a server-side control. It drives the platforms in the table above; it doesn’t substitute for any of them. The clean division: Claude covers judgment — review, refactoring, documentation drafting — the platform covers guarantees.

Decision 2 · AI models & how we reach them

Bedrock is settled. The open question is the front door.

We know we want AI models bought and governed through AWS Bedrock — one centralised place to purchase, one place to control access, one vendor already onboarded, one bill we already reconcile. That part is no longer under debate. What remains is the interface: a VS Code extension, the Claude Desktop app, or a self-hosted LibreChat instance sitting in front of every model Bedrock offers. Each has a different reach, a different governance story, and a different amount of work for us.

Recommendation: all three, in this order. (1) Claude Code on Bedrock, now — the CLI and VS Code extension pointed at our AWS account. (3) Claude Desktop only if someone specifically wants it — it works, but it is locked to Anthropic models and configured per machine. Why Bedrock — restating the settled part briefly

So the reasoning is on the record before the interface argument starts.

  • One buying point, one governance point. Every model — today’s and next year’s — is purchased and controlled in the same place, with IAM as the access boundary and CloudTrail as the record. No second procurement, no second admin console, no second audit story.
  • No new vendor. AWS is already onboarded, and inference runs on AWS infrastructure under the AWS data-processing relationship. The client applications become software we install, like any other tool. This position is directionally sound but needs Legal in writing — the tools’ own licence terms still apply.
  • Price parity, not a discount. Bedrock’s per-token list rates for Claude models match Anthropic’s own API rates. If we require US-region inference — likely for a bank — regional endpoints carry roughly a 10% token premium. Bedrock should be argued as a governance and vendor decision, not a cost saving.
  • A second model family costs no new onboarding. The internal suggestion that we should run two independent AI stacks is satisfied inside Bedrock: Anthropic, Amazon Nova, Meta, and Mistral sit side by side under one set of guardrails and one bill. Resilience without a second procurement cycle.
  • Things that only exist on this path: Bedrock Guardrails (content and PII policy enforced at the API layer, before a response is returned), Knowledge Bases (managed retrieval over our own documents), PrivateLink and customer-managed KMS keys, model-invocation logging to S3 or CloudWatch, 50% batch-inference discount, and prompt caching.
  • What we give up by not buying a vendor Enterprise plan: the vendor-side admin plane — enforced SSO/SCIM in their console, per-user spend caps, and the Compliance API that Varonis ingests for conversation-level oversight. On Bedrock we rebuild those with AWS parts: IAM Identity Center, Budgets, and invocation logging. Solid controls, but ours to assemble and defend.

An open-source chat platform that connects directly to Bedrock and serves every model family Bedrock offers from one interface — with an admin panel, role-based access control, and Entra SSO. This is the option that turns Bedrock from a developer resource into a bank-wide capability.

RecommendedAll Bedrock models$0 licenceWe host, patch & operate it

What it costs — infrastructure only

  • $0 licence. Open source. The entire bill is AWS infrastructure, and it’s small relative to everything else in this document.
  • Pilot — EC2 + docker-compose: ~$90–110/mo (~$1,100–1,300/yr). One t3.large, 100 GB gp3, one load balancer, the document store running in a container on the same volume. Right for a sandbox and a first production wave.
  • Production — ECS Fargate: ~$250–350/mo (~$3,000–4,200/yr). Two tasks behind a load balancer, managed document store, automated backups. No instance to patch.
  • Scaled — EKS: ~$400–500/mo (~$4,800–6,000/yr). Adds the $73/mo control-plane charge; only sensible if we are already running EKS for something else.
  • Tokens are unchanged. They bill to Bedrock at the same rates as the other two options — the interface choice never affects token cost.
Infrastructure figures modeled from AWS list pricing (July 2026) for us-east-1 on-demand — directional, and dependent on the final architecture chosen in the sandbox spike.

Where it’s strong

  • Every Bedrock model behind one URL — Anthropic, Amazon Nova, Meta, Mistral. One interface instead of a separate app per vendor, which is the multi-stack resilience argument satisfied without new tool sprawl.
  • A real admin plane. Built-in Admin Panel with ADMIN and USER system roles out of the box: manage users, adjust model availability, set rate limits, inspect configuration — through a UI, not hand-authored IAM policy.
  • Custom roles and permissions mapped to synced Entra ID groups — so access follows the directory we already run, and joiner/mover/leaver works the same way it does for GitHub.
  • Per-group model governance — the single biggest lever on token spend. Let engineering reach the expensive reasoning models; give general staff a cheap one. Neither of the other two options can express that rule at all.
  • SSO via OIDC or SAML at no extra cost — notable because most commercial chat products put SAML behind a premium tier.
  • One searchable home for prompts, answers, and files. Search across every message and document in one place, persistent memory across conversations, agents with file handling, MCP connections, web search, and in-chat artifacts — React, HTML, and Mermaid diagrams rendered directly in the conversation.
  • Conversation data sits in our VPC, in our database. That makes retention, legal hold, and export something we satisfy directly rather than through a vendor API we don’t control.

Where it runs out

  • It’s ours to run. Patching, upgrades, backups, capacity, and on-call for an application the whole bank may come to depend on. This is the same trade that appears in every self-host option in this programme, and it should be priced in engineering time, not just dollars.
  • Open-source onboarding review required. A new dependency in the stack, subject to the same review as any other tool we take on — and no vendor SLA behind it.
  • Web-only. No desktop application, and no local-filesystem agent work — that stays with Claude Code. Not a blocker, but worth stating rather than discovering.
  • The capability list above comes from project documentation, not from our own pilot. Verify SAML SSO and the granularity of the RBAC model against the exact version we deploy. Documentation is not a proof of deployment.
  • Conversation oversight is a build, not an integration. Varonis has no LibreChat connector; feeding conversation content to Varonis or Rapid7 is work we would scope and own. The offset is that the data is in our own database, which makes the build tractable.
  • It becomes a production dependency. Once the bank uses it daily, an outage is a business event. That argues for the Fargate architecture rather than a single EC2 instance once it moves past pilot.

Where the VS Code–only path specifically runs outAli’s ask

Called out separately because the question was asked directly: what does this option lack in the grand scheme?

Five things, in order of how much they matter to a bank. (1) Reach — it serves developers and no one else, so on its own it produces a development tool rather than an organisational capability. (2) Governance — no console; “which teams can use which models, at what rate limit” becomes IAM policy someone hand-maintains per account, and there is no way to answer that question from a UI in an audit. (3) Retention and oversight — nothing captures conversation content unless we explicitly enable Bedrock model-invocation logging, and then reviewing it is our job; there is no vendor Compliance API and therefore no Varonis conversation feed. (4) Cost control — AWS Budgets alerts after spend, so there is no hard per-user ceiling on a runaway agent session. (5) Institutional memory — no shared history, no org-wide search over prompts and answers, no artifacts to hand to someone who doesn’t write code, so nothing accumulates. None of this makes it the wrong first step. It makes it an incomplete last step.

Account structure, and tracking spend per personAli’s ask

The review raised whether we’d need an AWS account per person to attribute token consumption, and whether this warrants its own organisational unit. Both have clean answers.

1 · Sandbox

sandbox_ai

A new account under the existing Sandbox OU. Enable Bedrock, wire all three front doors, stand up LibreChat on a single EC2 instance, and prove out the invocation-logging story with nothing at stake.

2 · Production

One AI account

One production account per environment — not one per person. Bedrock access granted through IAM Identity Center against Entra groups, exactly as for every other AWS workload.

3 · Attribute

Inference profiles

Bedrock application inference profiles tag consumption per user, team, or application inside a single account, and CloudTrail attributes every invocation to an IAM identity. This is the mechanism the per-person tracking question was reaching for.

4 · Cap

Budgets & alerts

Per-profile AWS Budgets with alert thresholds, plus LibreChat’s own per-role rate limits as the preventive layer in front of them. Alerting is reactive; the rate limits are what actually stop a runaway.

  • An account per person is not needed, and would be a mistake. Application inference profiles plus CloudTrail give per-person attribution inside one account. Sixty AWS accounts to answer a cost-reporting question would create sixty things to govern, patch policy on, and eventually clean up.
  • On the AI_Access OU question — probably not, and here’s the reasoning. Organisational units are policy boundaries, not billing boundaries. Cost separation already comes from the account and the inference profiles. A dedicated AI account under the existing Infra or AI/ML Dev OU, with service control policies scoped to Bedrock, achieves the same control with one less structure to maintain. A new OU is only worth it if a different team owns the guardrails — which is a governance question, not a technical one, and worth putting to the cloud-governance conversation rather than deciding here.
  • Enable model-invocation logging on day one, in the sandbox. It is trivial to turn on at the start and awkward to backfill later, and it is the only thing that makes conversation content available for review at all on the Bedrock path. Log to S3 with Object Lock so the retention story matches how we handle other log sources.
  • Use Bedrock Guardrails as the policy layer, not just the model’s own judgment. Content and PII filters enforced at the API boundary apply to every front door at once — VS Code, Desktop, and LibreChat — which is a governance advantage no per-application setting can match.

Keeping two model families consistent

Raised internally: if we deliberately run more than one model family for resilience, how do we stop them behaving like two unrelated tools?

The distinction that matters

Same toolbox, not the same brain

Two different models from two different labs will never reason identically, and chasing that is wasted effort. What is genuinely achievable — and what actually determines consistent output — is giving both the same tools, the same data access, and the same written task definitions. That is a solvable engineering problem, and Bedrock plus MCP solves most of it.

How it’s wired

Four things to standardise

Tools: one MCP server per system — GitHub, Jira, our databases — and any MCP-capable client plugs into the same one, so there is no per-model integration work. Instructions: task definitions as plain files in the repository rather than per-vendor prompt configuration. Ground truth: both graded against the same test suite, linter, and CI checks — this is what actually keeps output consistent. Review points: defined places where a human compares outputs before merge, especially early on.

Why this connects back to Bedrock: MCP is the reason a second model family is cheap rather than a second integration project. Build one MCP server per system and every compatible client — whichever model is behind it — reaches it the same way. Combined with LibreChat as the front door, the whole multi-model story becomes one interface, one set of tools, one governance plane, and one bill. That is a materially better position than running a separate application per vendor.

What Jira enables beyond ticketingAli’s ask

The review asked specifically about automation, the GitHub and Confluence integrations, self-service, change management, and email-to-ticket. Each is below.

Automation

The queue populates itself

Alerts from Defender, Rapid7, and Proofpoint open tickets automatically. Portal requests route by category, priority, and location without a human triaging them. Technicians spend their time triaging and resolving rather than transcribing — and every ticket that self-creates is a ticket nobody had to type.

GitHub integration

Code and work become one record

A branch, commit, or pull request references its issue and the ticket updates itself — status, linked commits, deployment. This is the connective tissue between the two decisions in this document: a code change, the security finding that prompted it, and the change record that authorises it all sit on one timeline instead of three systems.

Confluence integration

Answers written once, reused everywhere

The knowledge base behind the self-service portal, holding runbooks, architecture decisions, and post-implementation reviews linked back to the change that produced them. Markdown in a GitHub repository can auto-publish into it, so documentation stays current through the same pull-request workflow as the code.

Self-service

Routine requests resolve without a technician

A modern portal backed by that knowledge base deflects the repeat traffic — password resets, access provisioning, how-tos — before it reaches a queue. First-contact resolution improves while the manual queue shrinks, which is the mechanism by which a smaller team absorbs more volume.

Change management

The CAB packet assembles itself

Every change carries its approvals, risk rating, and post-implementation review in one ITIL-aligned record. The weekly packet and the monthly ISC report are generated from live data rather than rebuilt by hand each week, with NIST SP 800-53 control mapping already attached. The audit trail accrues as work happens instead of being reconstructed before an examination.

Email to ticket

The mailbox becomes a queue

An email to a monitored address creates a ticket with the sender as reporter and the thread as history. Agent replies go back out as email, so the requester never has to learn a new tool — the change is invisible to them and total for us. Volume, first-response time, and SLA attainment per queue come out of the box, which are numbers we currently do not have at all.

Change management, end to end

Where the manual overhead is heaviest today, and where the automation is worth the most.

1 · Raise

Auto-routed

A change is logged — or opens automatically from a GitHub merge or a monitoring alert — and enters the ITIL change workflow with the right approvers already attached.

2 · Approve

Risk-scored

Configurable approval chains and risk-assessment templates aligned to bank standards capture sign-off and risk level as part of the workflow, not as a separate document.

3 · Review

Documented

Post-implementation reviews live in Confluence and link back to the change that produced them, so the record completes itself without a second round of data entry.

4 · Report

Assembled

The weekly CAB packet and the monthly ISC report pull straight from these records, with control mapping attached. The meeting starts from live data rather than from someone’s Friday afternoon.

IT and Facilities specificallyAli’s ask

The review noted Jira is being considered as a replacement for current help-desk and facilities workflows, not only for engineering work. That changes the design in four concrete ways.

IT service desk

What changes for the help desk

Multiple queues with their own request types, SLAs, and routing rules replace one undifferentiated ticket list. Security alerts arrive as tickets rather than email. Asset management (a Premium feature) links a ticket to the actual machine it concerns. Reporting on volume, first-response time, and SLA attainment exists by default — which is the part that makes staffing decisions defensible rather than anecdotal.

Facilities

What changes for facilities

PDF and LAN forms become portal request types with structured fields, so a request arrives complete instead of needing a follow-up email. Location becomes a routing dimension, which matters across branches. Work orders carry SLAs and an assignee. Recurring maintenance can be scheduled rather than remembered. Facilities requesters need no licence — only the agents working the queue do.

  • Multiple queues is the structural change — IT, Facilities, InfoSec, HR, Retail Ops, and Marketing each get their own desk with its own request types, SLAs, and routing, all inside one platform and one licence pool. Today those are six different intake paths in six different tools.
  • Replacing PDF forms is worth more than it sounds. A structured request type validates its own fields, routes on them, and reports on them. A PDF does none of those things, and every incomplete one costs a round trip.
  • Email-to-ticket is the adoption strategy, not just a feature. Nobody outside the technology departments has to change how they ask for something on day one. They keep emailing; the work becomes tracked anyway. Portal adoption can follow at its own pace.
  • The technology departments should pilot first — Software Engineering, Data Engineering, AI/ML, Networking, and InfoSec engineering — before the IT help-desk phase. Small, new, and green-field is the ideal proving ground, and it means the first bank-wide wave lands on a configuration that has already been used in anger.
